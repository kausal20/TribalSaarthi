# Claude Code / Codex build prompt — SIH26239

You are a senior product engineer. Build a **small, honest, working national-screening prototype** for SIH26239, an AI-enabled scholarship and fellowship management platform for Scheduled Tribe (ST) students. Deadline: less than 24 hours. Do not build a production Ministry system. Read `PRD.md`, `TRD.md`, `architecture.md`, and `design.md` in full before coding. Treat their acceptance tests and scope limits as requirements. If any detail is missing, choose the smallest safe implementation and record the assumption in `README.md`. Never invent eligibility criteria, approved selection rules, live integrations, verified identities, real scholarship decisions, or an AI model you have not actually implemented.

Context: The SIH brief requests one configurable platform covering applications, document upload, eligibility/document scrutiny, deficiency resolution, human-supervised selection support, applicant tracking, and administrative monitoring. NFST and NOS are *real, distinct* Ministry schemes. The prototype will demonstrate two *illustrative* configurations, not claim to encode authoritative current criteria. Official background: https://tribal.nic.in/ScholarshiP.aspx ; SIH26239 mirror: https://zaidsayyed.in/tools/sih-problem-statements/sih26239 . Verify rules from current official scheme PDFs before promoting any demonstration rule to a factual eligibility claim.

FIRST: summarize the problem, actors, proposed MVP, risks, and milestone plan in <= 250 words. Then inspect the workspace. If files are missing, ask me to place them there. Do not begin coding against guessed requirements.

Build a responsive prototype with (1) student side; (2) officer side; (3) admin-configured scheme definitions stored as versioned data. Demonstrate same application component and rule evaluator against two different scheme configurations; difference must come from data, not hard-coded conditional pages. Include demo mode with fictional applicant accounts, visible persistent prototype disclaimer, reset-demo action, fictional sample document files, no real PII. Applicant must be able to choose scheme, complete form, attach sample documents, submit, see exact rule/required-document deficiencies, fix/resubmit, and see event timeline. Officer must see queue, original attachments and rule evidence, request a correction with a reason, manually mark `READY_FOR_SELECTION_REVIEW`, and record a simulated post-selection follow-up status. No AI or automatic system may grant or reject funding. Provide an admin-friendly read-only scheme comparison plus an editable, versioned rules configuration if feasible after core flow works. Include a tiny summary dashboard computed from actual demo records, not invented KPIs. Optional guided assistant must use deterministic responses grounded only in configured demo requirements; label it `Guided demo assistant (not an LLM)`.

Do not implement third-party government portal automation, Aadhaar/DBT/bank integrations, real OTP, actual award ranking, certificate authentication, or claim real OCR unless a running OCR implementation is demonstrated with its errors and a manual correction path. Treat `uploaded` as distinct from `verified`. Do not transmit sample documents to an external LLM. Avoid dependence on paid services and API keys. If actual OCR cannot be made reliable in the time box, defer it explicitly; rules checks are not AI.

Recommended stack if no repo exists: React + TypeScript + Vite with CSS, simple client-side localStorage persistence with a versioned schema; no backend needed for the 24-hour screening build. If a backend already exists and works, keep it rather than rewriting. Never present localStorage as production security. Ensure predictable state transitions, file type/size guards, helpful validation, keyboard navigation, mobile layout, and no misleading fake success messages. Use browser-stored fictional demo metadata/files only; after reload, keep application, status, and event history (store safe file metadata, or persist safe demo files with a size cap). If a real backend is added, document it, test it, and keep scope.

Acceptance demo:
1. Reset demo. Student `Asha Demo` chooses Scheme A, leaves one required document missing, submits, and sees a named deficiency and exact rule.
2. Student attaches the missing sample file and resubmits; application ID remains stable and event timeline persists after refresh.
3. Officer sees same application, checks its original evidence, requests a correction with a reason; student sees it and corrects it.
4. Officer manually moves it to `READY_FOR_SELECTION_REVIEW`; student sees status change. Officer can record a *simulated* later follow-up status; not an actual award/payment.
5. A second fictional applicant applies to Scheme B. Show a different document rule applies using the same form/checker. Change configuration data (not code), reload, and show that the checker responds. Explain version handling for previously submitted applications.
6. Show missing/wrong type/oversized file, empty mandatory field, invalid status transition, persistence after reload, and reset behavior.

Plan and execute in vertical slices. First make one working end-to-end scheme journey; next add second data-driven scheme; next officer reasons/timeline; next UI refinement and optional assistant; OCR only last if time. After each slice run tests, report exactly what works and what remains simulated. Add README with local install/run instructions, demo credentials (if any), illustrative rules, test steps, caveats and planned real architecture. Stop before deadline and prioritize a working clickable demo plus screen recording over extra features. Never report a passing test that has not run. Clearly distinguish 'working', 'simulated' and 'future scope' in all UI copy and final summary.
